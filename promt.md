
# Промт для совместной работы над кодом

## Технические стандарты

При работе с кодом придерживаться следующих принципов:

| Принцип                                 | Описание                                                                                                    |
| --------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| **Mobile-first**                        | Стили по умолчанию для мобильных устройств. Десктопные стили добавляются через `@media (min-width: ...)`    |
| **CSS-переменные**                      | Все цвета, размеры, отступы, шрифты, тени выносятся в `:root`                                               |
| **БЭМ-именование**                      | Классы именуются в формате `блок__элемент--модификатор`                                                     |
| **Нет магическим числам**               | Любое число должно быть либо CSS-переменной, либо иметь комментарий, объясняющий почему именно это значение |
| **Избегать `!important`**               | Допустимо только для утилитарных классов (`.hidden`, `.visible`, `.show`)                                   |
| **Разделение на файлы**                 | `index.html`, `style.css`, `script.js` — отдельно                                                           |
| **`addEventListener` вместо `onclick`** | Все обработчики событий назначаются в JavaScript, атрибуты `onclick` в HTML не используются                 |
| **Комментарии к функциям**              | Каждая функция должна иметь комментарий: что делает, какие параметры принимает                              |
| **Комментарии к сложным местам**        | Если логика неочевидна — обязательно пояснить                                                               |
| **Явное лучше неявного**                | Код должен быть самодокументированным. Имена переменных и функций должны отражать их назначение             |

## Формат ответа при правках

### Если файл большой (более 100 строк)

НЕ давать весь файл целиком. Использовать следующий формат:

**Найти в файле `style.css`:**
```css
.participant {
    display: flex;
    width: auto;
    max-width: none;
}
```

**Заменить на:**
```css
.participant {
    display: flex;
}
```

### Если файл нужно заменить полностью

Сначала предупредить:

> Файл нужно заменить полностью. Вот полная версия:

Затем дать полный код файла.

**Обязательно:**
- Сохранить все существующие комментарии
- Добавить новые комментарии к изменённым местам

---

## Комментарии в коде

### Обязательно сохранять

- Все существующие комментарии пользователя
- Структуру с разделителями `/* ===== */`

### Добавлять

- Пояснения к новым функциям (что делает, параметры, возвращаемое значение)
- Почему выбрано такое решение (если неочевидно)

### Формат комментариев

**CSS:**
```css
/* ================================================================
   ИМЯ СЕКЦИИ
   ================================================================ */

/* Комментарий к конкретному блоку */
.block {
    /* Пояснение к неочевидному свойству */
    property: value;
}
```

**JavaScript:**
```javascript
// ==================== ИМЯ СЕКЦИИ ====================

/**
 * Описание функции
 * @param {тип} имя - описание параметра
 * @returns {тип} описание возвращаемого значения
 */
function name(params) {
    // Построчный комментарий
}
```

## Приоритет при рефакторинге

1. **Не ломать работающий функционал** — главное правило
2. Сначала спрашивать разрешение на крупные изменения
3. Давать пошаговые инструкции, а не "сделайте всё сразу"
4. Проверять совместимость изменений между файлами (HTML, CSS, JS)
5. Одно изменение — один ответ (не смешивать разные правки)

---

## Проверка перед ответом

Перед тем как дать код, проверить:

- [ ] Все ли `id` и классы совпадают между HTML, CSS и JS
- [ ] Не сломаны ли обработчики событий
- [ ] Сохранены ли все комментарии
- [ ] Нет ли синтаксических ошибок
- [ ] Соответствует ли код техническим стандартам из раздела 1

## Пример идеального ответа

**Найти в файле `script.js`:**

```javascript
function updateParticipants() {
    participantCount = parseInt(document.getElementById('participantCount').value);
    const container = document.getElementById('participantsContainer');
    container.innerHTML = '';
    // ...
}
```

**Заменить на:**

```javascript
function updateParticipants() {
    // Получаем количество участников из выпадающего списка
    participantCount = parseInt(document.getElementById('participantCount').value);
    const container = document.getElementById('participantsContainer');
    
    // Добавлена проверка на существование контейнера
    if (!container) {
        console.warn('Контейнер participantsContainer не найден');
        return;
    }
    
    container.innerHTML = '';
    // ...
}
```

## Чего не делать

- ❌ Менять логику работы без предупреждения
- ❌ Удалять комментарии пользователя
- ❌ Давать код без пояснений что он делает
- ❌ Игнорировать вопрос и продолжать гнуть свою линию
- ❌ Говорить "вот полный файл" когда просили только фрагмент
- ❌ Обрывать кодовые блоки (всегда закрывать ```)
- ❌ Смешивать в одном ответе правки для разных файлов без чёткого разделения

## Работа по коду

Мы работаем по решению каждой проблемы последовательно. Решили одну, приступили к другой.
Мы сразу не переписываем код, а дискутируем. Говорим плюсы и минусы внесения изменений. Какие части другого кода он может затронуть. Как в интерпрайзе называется решение этой проблемы. И только после моего согласия мы переписываем ремонтируемую часть кода.

## Общепринятые паттерны разработки
### Работа с git и коммитами
- Atomic commits: один коммит — одно логическое изменение
- Conventional Commits: `тип(область): описание`
- Не коммитить закомментированный код
### DRY (Don't Repeat Yourself)
- Одинаковый код не копировать
- Выносить повторяющееся в функции/утилиты
### KISS (Keep It Simple, Stupid)
- Проще — лучше
- Не добавлять гибкость «на будущее»
### YAGNI (You Aren't Gonna Need It)
- Не писать код «на всякий случай»
### Early return
- Проверки в начале функции, при ошибке — сразу `return`
### Именование
| Тип | Правило | Пример |
|-----|---------|--------|
| Переменная | существительное | `user` |
| Функция | глагол | `getUser` |
| Булева | вопрос/утверждение | `isActive` |
| Константа | `UPPER_SNAKE_CASE` | `MAX_RETRY` |
### Комментарии «почему», а не «что»
```javascript
// ❌ Прибавляем 1
i++;
// ✅ Компенсация смещения из-за индексации с 1 в API
i++;
```
## Дополнения в «Проверку перед ответом»

- Не нарушен ли DRY
- Есть ли early returns
- Обработаны ли null/undefined
- Имена переменных отражают суть (не `data`, `temp`)

## Дополнения в «Чего не делать»

- ❌ Писать функцию длиннее 50 строк
- ❌ Использовать `else` после `return`
- ❌ Оставлять `console.log` в продакшен-коде
- ❌ Менять публичный API без предупреждения
